# 書き込みの後に、LSP の診断で新しく増えたエラーを、MCP の write の報告に付ける

## 状況

edo は書き込みで構文エラーが増えたことを報告するが、型の不一致や存在しない名前のような、構文の外のエラーには気づけない。エージェントはビルドやテストを回すまで、自分の書き込みが壊したことを知らない。言語パッケージに LSP サーバーの設定を書けるようにして、書き込みの直後に診断を受け取りたい。

LSP サーバーは起動とプロジェクトの読み込みに時間がかかる（大きな Rust のプロジェクトで数十秒）。edo の CLI は 1 回ごとに終わるプロセスで、MCP サーバー（`edo mcp`）は会話の間ずっと動いている。

## 決定

- 提供するのは、書き込みの後の診断だけ。定義や参照のたどりは、診断が動いてから考える。
- LSP は MCP のプロセスの中だけで動かす。（言語、プロジェクトのルート）の組ごとに、最初に必要になったときにサーバーを起動し、MCP のプロセスが終わるまで使い回す。CLI の write には診断を付けない。
- 言語パッケージの `[package.lsp]` に `command`（配列、シェルを通さない）、`root_markers`（いちばん近い親ディレクトリをルートにする）、`language_id`（省略すると `package.name`）を書く。`[package.lsp.distribution]` に `type = "mise"` と `tools` を書くと、mise があれば `mise exec <tools> -- <command>` で起動し、初回に mise が入れる。mise がなければ `command` を PATH から探す。edo 自身はサーバーを入れない。
- 書き込みは待たせない。診断は最大 2 秒待ち、届かなければ報告に `"lsp": "starting"` を付ける。サーバーが見つからないことは書き込みには出さず、`edo lang list` に出す。
- 報告するのは、書き込んだファイルの、重大度がエラーの診断のうち、新しく増えたものだけ。`warnings.new_lsp_errors` に `line` と `message` で返す。
- 「新しく増えた」は、前の診断を書き込み後の行に移し、「文と行」の組で後にだけあるものとする。行の移し方は、書き込みが書き換えた箇所ごとに作る `Hunk`（前の行の範囲 → 後の行の範囲）から求め、書き換えた行にあった前のエラーは比較から外す。構文エラーも、文が `syntax error` のエラーとして同じ関数で判定する（報告の形 `new_syntax_errors` は変えない）。
- 前の診断は「ある内容に対する診断」の覚え書きから取る。ファイルごとに、サーバーに最後に渡した内容と、その診断を 1 組覚えておき、同じ内容なら待たずに使う。edo の外で書き換えられた後の最初の書き込みだけ、前と後の 2 回を待つ。edo の外の変更で増えたエラーは報告しない。
- LSP のクライアントの中心は workspace の `crates/edo-lsp-client` に置く。edo の言語パッケージのことは知らない。`lsp-types` と、`lsp-server` のメッセージの読み書きを使い、テストは同じプロセスの中の偽のサーバーとつなぐ。
- 組み込みの言語には、Rust（rust-analyzer）、TypeScript・TSX・JavaScript（typescript-language-server）、Python（pyright）、Go（gopls）を書く。

## 結果

- 得たもの: エージェントは、書き込みの報告だけで、型エラーなどを書き込んだその場で知れる。エラーが増えたときだけ報告に付くので、コンテキストは増えない。同じファイルへの続けての書き込みは、待つのが 1 回で済む。構文エラーと LSP の判定が 1 つの仕組みになる。
- 失ったもの: CLI の write では診断が出ない。別のファイル（呼び出し元など）で増えたエラーは報告しない。2 秒で届かない診断は報告されず、エージェントは `starting` しか知らない。LSP サーバーは MCP のプロセスが終わるまで動き続ける。
- 採らなかった案:
  - ユーザーごとのデーモンで CLI と MCP の両方から使う案は、版の食い違い、起動の競合、ソケットの片付けといった問題を抱えるので、CLI の診断が必要になるまで作らない。
  - 書き込みのたびに前の内容を送り直して 2 回待つ案は、待ち時間が 2 倍になるので、覚え書きにした。
  - 「行の文字」で前後のエラーを対応づける案は、書き込みが持つ正確な書き換えの対応を捨てる推測で、`}` のような同じ文字の行が多い場所で誤るので採らなかった。
  - サーバーが見つからないことを言語ごとに最初の 1 回だけ報告する案は、覚えておく状態と、それがいつ消えるべきかという特別扱いが増えるので採らなかった。
  - edo がサーバーを入れる案（mason.nvim のような形）は、配布の形と OS ごとの違いを扱う大きさになるので、mise に任せた。
