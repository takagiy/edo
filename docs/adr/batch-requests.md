# read と write は、頼み事の配列を 1 回で受け取る

## 状況

エージェントは、関連する定義をいくつも読んだり、同じファイルの何か所かを直したりする。read と write は 1 回の呼び出しで 1 件しか受け付けなかったので、その分だけ呼び出しが増えた。write では、エージェントが edo をやめて perl の一括置換に逃げることもあった（[アイデア](../idea/fewer-calls.md)）。

## 決定

- read は `{path, scope}` の配列（MCP の `reads`）を、write は `{path, scope, before, after, mode, all_matches}` の配列（MCP の `edits`）を受け取る。規則は「頼み事が複数なら配列」の 1 つだけ。今までのトップレベルの書き方は、配列の先頭の 1 件として扱う。
- read は、要素が 2 件以上なら、glob で読むときと同じく各要素の前にパスの行を付ける。
- write は、すべての要素を呼び出し前のファイルに照合する。前の要素が書いた結果に次の要素を照合することはしない。ファイルごとに見つかった箇所をまとめ、後ろの箇所から書き換える。`all_matches` で一致が複数あるときと同じ仕組みで済む。
- write は、すべて書くか、何も書かない。どれかの要素が見つからない、一致が複数ある、書き換える範囲がほかの要素と重なる（`overlap`）、のどれかなら、ファイルには何も書かず、失敗だけを報告する。
- 失敗には、要素が 2 件以上なら何番目かを `item` で付ける。`replaced` は要素の順に並べる。
- CLI の read は複数の対象を並べて受け取る。CLI の write は 1 ファイルのままで、標準入力にコンフリクトマーカーの組が複数あれば、組ごとに書き換える。

## 結果

- 得たもの: 関連する読み書きが 1 回の呼び出しで済む。複数箇所の書き換えが途中で失敗しても、ファイルが半端な状態で残らない。
- 失ったもの:
  - glob の write は、一致が複数あるファイルが 1 つでもあると、ほかのファイルも書かなくなった。前は書けるファイルだけを書いていた。
  - write のエラー（言語パッケージがない、scope が見つからない、など）は、`file` 付きの報告として返るようになった。
  - 2 つ目以降のファイルを書く途中で入出力のエラーが起きると、先に書いたファイルだけが書き換わった状態で残る。
  - CLI の write で、標準入力にコンフリクトマーカーの組が 2 つ以上あると、今までは 2 つ目以降を無視していたが、これからは書き換える。

## 採らなかった案

- scope の中でカンマ区切りにする（`a,b`）: 複数を渡す書き方が、配列とカンマの 2 通りになる。カンマは文字列の中の小さな独自文法で、データの形としても素直ではない。
- 前の要素が書いた結果に次の要素を照合する: 要素ごとに解析し直し、行のずれも直す必要がある。今の不便を解消するのには要らない。
