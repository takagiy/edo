# エージェントの tool call と token を減らす

## きっかけ

MISON の組み込みと監査の修正（2026-11-03）を、edo を使って進めた。その中で、edo では足りずに呼び出しを重ねた場面や、perl などのほかの手段に逃げた場面があった。下の案は、その場面から拾ったもの。効果の大きい順に並べている。

## 案

### 行範囲がファイルの末尾を越えたら、末尾で切って返す

行数を知らずに大きめの範囲を読もうとして、`out_of_range` に 4 回当たった（`lib.rs 1-60`、`mcp.rs 228-310`、`edit.md 1-40`、`lsp.rs 116-290`）。どれもエラーで行数を知ってから読み直している。範囲を末尾で切って返し、切ったことを一言添えれば、この読み直しは要らない。始まりの行が末尾を越えたときだけ、エラーのままにする。

### 1 回の write で複数箇所を直す

1 つのファイルの複数箇所を直すとき、edo では箇所ごとに 1 回呼ぶことになるので、perl での一括置換に逃げた。およそ 8 回あった。テストの期待値の書き換えや、`[[2,2]]` を `"2-2"` に変える 4 か所がその例。そのうち 1 回は、置換が当たりすぎて元に戻す手間も出た。

`edits: [{before, after}, ...]` を受け取り、すべて一致するときだけまとめて書く。行のずれは、`all_matches` と同じく後ろの箇所から適用すれば、そのまま扱える。

決着: read とそろえて、頼み事の配列を受け取る形にした（[ADR](../adr/batch-requests.md)）。

### 小さいファイルは中身を隠さずに全部見せる

`docs/test-list/edit.md`（22 行）を scope なしで読むと、見出しの `# 編集` しか返らず、行範囲を指定して読み直した。数十行のファイルなら、中身を隠しても節約にならない。決めた行数より短いファイルは全文を返す。

### 1 回の read で複数の定義を読む

`package_dir` と `try_install` のように、関連する関数を 1 つずつ読む場面が何度もあった。`scope` に `a,b` のような複数指定を許せば、まとめて読める。

決着: カンマ区切りではなく、`{path, scope}` の配列を受け取る形にした（[ADR](../adr/batch-requests.md)）。

### LSP の準備ができていないときは待たない

Rust ファイルへの write は、ほぼ毎回 `warnings=(lsp=starting)` を返し、そのたびに最大 2 秒待った。診断が実際に届いたのは 2 回だけで、そのうち 1 回は古い診断だった可能性がある。`lines` を定義した直後の write に「`lines` が見つからない」というエラーが返っている。原因はまだ調べていない。

サーバーの準備ができる前は待たずに何も返さないようにすれば、`starting` の表示と待ち時間の両方がなくなる。

### 報告のパスを作業ディレクトリからの相対パスにする

今は毎回 `file=C:/Users/takag/Codes/edo/src/matcher.rs` と書かれ、1 回の write ごとに 10 token ほど余分にかかる。MCP サーバーは作業ディレクトリの下で起動するので、その下のファイルは相対パスで足りる。

### 定義の後ろに挿入するときは、間に空行を入れる

`insert-after-matches` で関数を 1 つ挿入したら、次の定義との間の空行がなくなり、perl で直した。定義の前後に挿入するときは、隣の定義との間に空行を入れるのが自然。

### 監査で見送ったもの：起動のたびに全文法を読み込む

edo は起動のたびに、hook の呼び出しでも、組み込みのクエリを組み立て、インストール済みの wasm 文法をすべてコンパイルする。hook に要るのはファイルの拡張子だけ。組み込みだけの状態で測ると、空のプロセスより約 60 ms 余分にかかった。wasm パッケージを入れたときの遅さを測ってから、`Language` を最初に使うときに読み込む形にするか決める。
